# Android APK Requirements — Engineering Spec

**Date:** 2026-10-13
**Status:** Experimental. The APK builds and launches; most Pi-only subsystems are inert.
**Goal:** Record what it takes to build Hearth as an Android APK for a dedicated, wall-mounted kiosk tablet (generic arm64, Android 10+), what works after the scaffold landed, and what is still required before the APK is a full Hearth.

Fire OS and Play Store distribution are out of scope here. The CI job that builds the APK was added afterwards and is described under [The CI build](#the-ci-build).

## How to read this

Every claim carries one of two labels:

- **verified** — observed on 2026-10-13, either in the trial build or on the emulator run described under [Verification environment](#verification-environment).
- **assumed** — reasoned from the code or from Android platform behaviour, not observed. Treat as a hypothesis to test.

Unless a claim says otherwise, **verified** means the emulator. One real device had a smoke test when the scaffold landed: the release APK installs and launches on an Apolosign 21.5" calendar tablet (RK3576, arm64-v8a, Android 16 / API 36, 1080x1920 panel at 240 dpi), where Impeller selects Vulkan and LocalApiServer starts (**verified**). A second pass on that tablet, for the v1.21.0 readiness run (`2026-10-13-v1.21.0-release-readiness.md`), drove a debug APK of `daa74bf` over adb and the `:8090` API; rows it settled say **verified on the tablet**. Anything else that depends on a real tablet (Wi-Fi multicast, audio, Doze, RTSP and HLS playback) is still **assumed**.

## Build and sideload

### Prerequisites

- Flutter — the workflows pin **3.47.7**. The Android build was run on **3.47.6** (**verified**); 3.47.7 is **not verified** for Android.
- A JDK that AGP 9.1 accepts. JDK 17 works (**verified**); set `JAVA_HOME` if the default JDK is newer.
- Android SDK with licenses accepted. Gradle installs what is missing on first build: it pulled NDK 28.2.13676358 (2.2 GB), platform 35, platform 34, and CMake 3.22.1 on its own (**verified**). Platform 36 and build-tools 36.0.0 were already present.
- Network access at build time: `media_kit_libs_android_video` downloads prebuilt libmpv jars from `github.com/media-kit/libmpv-android-video-build` (v1.1.7) during the Gradle build (**verified**).

### Versions chosen

| Setting | Value | Why |
|---|---|---|
| `applicationId` / `namespace` | `com.hearth.hearth` | Matches `APPLICATION_ID` in `linux/CMakeLists.txt` and the `com.hearth/...` channel names. |
| `minSdk` | 29 | Android 10 is the oldest supported release. Flutter's default is 24. |
| `compileSdk` / `targetSdk` | 36 | Left on `flutter.compileSdkVersion` / `flutter.targetSdkVersion` so they move with the Flutter pin. |
| `ndkVersion` | 28.2.13676358 | Left on `flutter.ndkVersion` for the same reason. |
| ABIs | arm64-v8a, armeabi-v7a, x86_64 in debug | Flutter's debug default. Ship releases with `--target-platform android-arm64`. |

### Commands

```bash
flutter pub get
flutter build apk --debug
adb install -r build/app/outputs/flutter-apk/app-debug.apk
adb shell am start -n com.hearth.hearth/.MainActivity
```

For a device build, the script CI runs (see [Release signing](#release-signing) for which key it uses):

```bash
./scripts/build-android-apk.sh
```

It wraps `flutter build apk --release --target-platform android-arm64 --no-tree-shake-icons` and leaves `hearth-android-<version>.apk` and its `.sha256` in the project root.

`--no-tree-shake-icons` is required: `WebviewConfig.icon` builds `IconData` from a code point stored in config, and the release build fails without the flag (**verified**).

The debug APK is 228 MB because it carries three ABIs plus the Vulkan validation layer (**verified**). The release arm64 APK is 66 MB (**verified**).

To reach the web portal on an emulator: `adb forward tcp:8090 tcp:8090` (**verified**).

## What the trial build required

`flutter build apk --debug` succeeded on the first attempt against the unmodified scaffold. No Dart or Gradle source change was needed to get a green build (**verified**). What did need attention:

| # | Observation | Resolution |
|---|---|---|
| 1 | The first APK contained no `libmpv.so`: `pubspec.yaml` only carried the Windows and Linux media_kit libs (**verified** by listing the APK). | Added `media_kit_libs_android_video`. The rebuilt APK contains `libmpv.so` and `libmediakitandroidhelper.so`, and `MediaKit.ensureInitialized()` runs at startup without error (**verified**). Whether the first APK would have crashed at startup was not tested (**assumed**). |
| 2 | `flutter create` rewrote `analysis_options.yaml`, bumped `.metadata` revisions, dropped the `web` platform entry, re-resolved `pubspec.lock`, and added `test/widget_test.dart` (**verified**). | Reverted all of it except a new `android` entry in `.metadata`. |
| 3 | Flutter 3.47 re-adds an `analyzer: exclude:` block to `analysis_options.yaml` on **every** `flutter pub get` and build. It fires because `build/**`, `linux/**` and `windows/**` are not excluded, so it predates `android/` and happens on `main` today (**verified** in `flutter_tools/lib/src/migrations/analysis_options_migration.dart`). | `5f63da8` accepted the block; with `android/` present the migration then added `android/**`, which is now committed too. | 4 | `pubspec.lock` on `main` still pins the `bonsoir` family at 6.x while `pubspec.yaml` pins `bonsoir: 7.1.5`, so any `pub get` rewrites those six entries (**verified**). | The lock in this change carries the 7.x entries along with the new package. |

| 7 | `bonsoir`, `media_kit`, `sendspin_dart` and `flutterpi_gstreamer_video_player` raised no minSdk or NDK conflicts (**verified**). The GStreamer plugin registers no Android implementation, so it compiles to Dart only. | — |

## Launch behaviour

All **verified** on the emulator, from an APK built from a fresh clone and installed over a wiped app:

- Installs and cold-starts in about 2 s. Impeller selects the OpenGL ES backend.
- With an empty config the first screen is the setup wizard's Wi-Fi step, with an empty network list (`WifiService.scan()` returns `[]` off Linux). **Skip** leads to Home. This is the same first run Windows gets.
- Home renders; swiping pages works; the idle timer (120 s default) returns the pager from Settings to Home; a touch wakes it and navigation resumes.
- `adb logcat` shows no `FATAL EXCEPTION`, no `E/flutter`, and no unhandled Dart exception across that run.
- `hub_config.json` lands in `/data/user/0/com.hearth.hearth/files/`.
- The in-app on-screen keyboard appears on text-field focus; the system IME does not.
- On the Apolosign tablet (**verified on the tablet**, debug APK of `daa74bf`, portrait 1080x1920): install over the previous build and cold start; Impeller selects Vulkan; with `hub_config.json` removed the wizard's Wi-Fi step shows, **Skip** leads to Home, and the swipe row is Media, Home, Controls, Cameras, Settings; the 120 s idle timer returns the pager to Home; the in-app keyboard appears on a Settings text field while `dumpsys input_method` reports `mInputShown=false`; no `FATAL EXCEPTION` or `E/flutter` in logcat across the run.
- On the emulator, before immersive mode was added, the status bar and the tablet taskbar stayed visible and the app drew underneath the status bar. `main.dart` now sets `SystemUiMode.immersiveSticky` on Android; on the Apolosign tablet (Android 16) the status bar and navigation pill are hidden on Home and Settings (**verified**). Whether they stay hidden across every dialog, the keyboard and a return from another app was not exercised (**assumed**).

## Manifest

Declared in `android/app/src/main/AndroidManifest.xml`:

- `INTERNET`, `ACCESS_NETWORK_STATE` — every integration is a network client or server.
- `CHANGE_WIFI_MULTICAST_STATE` — mDNS, SSDP, GDM.
- `WAKE_LOCK` — keep-awake while playing; `wakelock_plus` arrives with `media_kit_video`.
- `android:usesCleartextTraffic="true"` — Home Assistant, Immich, Frigate and Plex are usually plain-HTTP LAN hosts. Cleartext requests to a LAN host were not exercised (**assumed**).
- `android:screenOrientation="fullUser"` — every orientation the user's rotation lock allows. The app narrows it at runtime from `displayOrientation`; the manifest value only governs the moment before Dart runs (**assumed**: a tablet held portrait may show the launch theme in portrait before a landscape lock applies).
- A second intent filter with `category.HOME` and `category.DEFAULT`, so Hearth can be chosen as the home app.
- `RECORD_AUDIO`, `MODIFY_AUDIO_SETTINGS`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK` — the voice satellite. `RECORD_AUDIO` and, on API 33+, `POST_NOTIFICATIONS` are requested at runtime the first time the satellite is enabled; the service only needs the first (**assumed**: the prompt has not been seen on a device, in immersive mode or as the HOME app).
- `.voice.HearthAudioService`, `foregroundServiceType="microphone|mediaPlayback"`, not exported, `START_NOT_STICKY`. No boot receiver: Dart starts it after config load, from the visible activity.
- `REQUEST_INSTALL_PACKAGES` — self-update through `PackageInstaller`. The user still grants "Install unknown apps" for Hearth and confirms each install.
- `.RestartActivity` in its own `:restart` process, not exported, translucent — relaunches Hearth after a restore.

The first four permissions are also contributed by plugins through manifest merging; they are declared explicitly so the app does not depend on that (**verified** in the merged APK, before and after).

## Kiosk requirements

Apart from immersive fullscreen and the HOME category, none of this is implemented. Everything in this section is **assumed** from Android platform behaviour unless marked.

- **Immersive fullscreen.** Done: `main.dart` sets `SystemUiMode.immersiveSticky` on Android (**verified** on the Apolosign tablet). An edge swipe still reveals the bars briefly; only lock task removes that.
- **Keep awake.** `FLAG_KEEP_SCREEN_ON` on the activity for as long as Hearth is foreground. The Pi never sleeps its panel; a tablet will, at its screen timeout.
- **Launcher vs. lock task.** Two tiers:
  - *HOME launcher* — done: the activity declares `category.HOME` + `category.DEFAULT`, so Android lists Hearth as a home-app candidate (**verified** on the Apolosign tablet, alongside its stock launchers). It is offered, not forced: the user picks it under Settings → Apps → Default apps → Home app, or `adb shell cmd package set-home-activity com.hearth.hearth/.MainActivity`. Choosing it, booting into it, and how an OEM launcher's own mode switching reacts were not exercised (**assumed**). No provisioning; the user can still reach the system via gestures and the notification shade.
  - *Lock task / device owner* — `adb shell dpm set-device-owner` on a factory-reset tablet with a `DeviceAdminReceiver`, then `startLockTask()` with Hearth allow-listed. Blocks the shade, recents and other apps, and unlocks silent updates and network provisioning. Needs a documented escape hatch.
- **Start at boot.** The HOME role covers it. Otherwise a `RECEIVE_BOOT_COMPLETED` receiver, which cannot start an activity from the background on Android 10+ without the overlay permission or device owner.
- **Long-lived sockets.** LocalApiServer, SSDP, GDM, MQTT and the HA and Music Assistant websockets all live in the Flutter isolate. They hold while the activity is foreground with the screen on. If the screen is ever allowed to turn off, Doze will suspend them: request a battery-optimisation exemption (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`) and consider a foreground service.
- **Multicast.** Hold a `MulticastLock` while any discovery responder is enabled (see the SSDP and GDM rows).
- **Power.** A wall tablet on permanent charge needs a charge limit to protect the battery. That is a device setting, not something the app can enforce without OEM APIs.

## Release signing

- `android/app/build.gradle.kts` signs release builds from `android/key.properties` (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`) when that file exists, and with the debug key when it does not, so contributors can still build. Both paths **verified** on the host with a throwaway keystore: `apksigner verify --print-certs` showed the keystore's certificate with the file present and `CN=Android Debug` without it.
- **The release keystore exists** (created 2026-10-14): PKCS12, RSA 2048, alias `hearth`, valid until 2054, certificate `CN=Hearth, O=Hearth`, SHA-256 `f3:2f:a9:0a:ed:9f:66:7c:50:58:2a:d5:dd:a9:db:87:b1:3d:e1:44:d7:71:ab:72:ca:50:54:9f:cc:e6:97:cb`. It lives outside the repo, with its password, on the maintainer's machine. Losing it means every tablet must uninstall and reinstall, losing `hub_config.json`, so it needs a backup beside that machine.
- CI has it as four secrets, on **both** GitHub and Gitea (set 2026-10-14): `ANDROID_KEYSTORE_BASE64` (`base64 -w0 hearth-release.jks`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. `scripts/build-android-apk.sh` writes the keystore and `key.properties` from them, and refuses to build when only some are set. A host run of the script with those four variables set printed "Signing with the release keystore", produced an APK whose `apksigner` certificate matches the digest above, and left neither file behind (**verified**). A CI run with the secrets has **not** happened yet.
- An APK installed before the keystore is debug-signed, and Android refuses to update it with a release-signed one (**assumed** from Android's signature check). Such a tablet takes one uninstall to move onto the release key; after that, release APKs update each other (**verified**, 1.21.1 → 1.21.2). To keep `hub_config.json` across that uninstall: copy it off with `adb exec-out run-as com.hearth.hearth cat files/hub_config.json` while the debug build is installed, install a debuggable build re-signed with the release key (`apksigner sign`) at a lower versionCode, copy the file back with `run-as`, then install the release APK over it. `POST /api/config` cannot restore it: `apiKey`, `plexAuthToken`, `dlnaUuid` and `setupComplete` are read-only there. Done this way on the Apolosign tablet (**verified**: the file came back byte-identical).
- `android/.gitignore` already excludes `key.properties`, `*.jks`, `*.keystore` and `local.properties` (**verified**).
- `versionCode` comes from the pubspec build number, which Hearth does not set, so a plain `flutter build apk` produces versionCode 1 (**verified** in the APK). Android refuses to install an update whose versionCode is not higher. `scripts/build-android-apk.sh` passes `--build-number` as `major * 1000000 + minor * 1000 + patch`: 1.21.0 builds as 1021000 (**verified** with `aapt2 dump badging`).

### The CI build

A `build-apk` job in both `build-pi-image.yml` workflows runs `scripts/build-android-apk.sh` on the triggers the Pi bundle already has: a `v*` tag, a manual dispatch, and on GitHub the weekly canary.

- **On a tag** it attaches `hearth-android-<version>.apk` and `hearth-android-<version>.sha256` to the release, beside `hearth-bundle-*`. `hearth-updater.sh` matches `hearth-bundle-*.tar.gz` only, so the Pi ignores them.
- **The bundle never waits on it.** On GitHub the release job runs when the bundle built, whatever the APK job did, and attaches the APK only if there is one. On Gitea the APK job runs after the bundle is published and uploads to that release.
- **On GitHub, a dispatch or the canary** keeps the APK as the `hearth-apk` artifact. On Gitea those runs build and discard, as they do for the bundle.
- The toolchain is JDK 17 (`actions/setup-java`), the SDK command-line tools with licenses accepted (`android-actions/setup-android`), and whatever Gradle then installs itself: platforms 34, 35, 36, build-tools 36, NDK 28.2.13676358, CMake 3.22.1. Roughly 3 GB on top of the Flutter SDK, from `dl.google.com`, Maven Central, the Gradle plugin portal and GitHub releases (libmpv jars). Nothing is cached: the cold build took about 220 s on the host, most of it downloads.
- **Verified on Gitea**, on a branch dispatch (run 1921): the self-hosted runner installed the toolchain from nothing and built the APK on Flutter 3.47.7 in 14 minutes, after the bundle job. That run had no tag and no signing secrets, so the release upload and the keystore path have **not run in CI**; the keystore path was run on the host only (Flutter 3.47.6, and again with the real keystore on 3.47.7 — see [Release signing](#release-signing)).
- **Not verified on GitHub.** The workflow there has not run with the new job.
- Keep the keystore passwords to letters and digits: they are written to `key.properties` unescaped.
- Pull requests still do not build the APK: `flutter analyze` and `flutter test` never run Gradle.

## Dependency-maintenance impact

Extends `docs/specs/2026-08-12-dependency-maintenance-process-design.md`.

- **The Flutter pin now gates an Android build too.** `compileSdk`, `targetSdk` and the NDK version follow `flutter.*`, so a Flutter bump silently changes all three and may require new SDK components (**verified** that they resolve from the Flutter SDK). The hardware-test rule for Flutter bumps should grow an "APK still builds and launches" step.
- **New moving parts**, watched only by the weekly GitHub canary and release builds: AGP 9.1.0 and Kotlin 2.4.0 (`android/settings.gradle.kts`), Gradle 9.3.1 (`android/gradle/wrapper/gradle-wrapper.properties`), `media_kit_libs_android_video` and the libmpv build it downloads, and the Android halves of `bonsoir`, `path_provider`, `video_player`, `volume_controller`, `wakelock_plus`, `screen_brightness`, `package_info_plus`, `sqflite` and `jni`.
- **Renovate will start seeing Gradle files** (**assumed** — `config:recommended` enables the `gradle` and `gradle-wrapper` managers; no Renovate run has happened since). Under the current `packageRules`, non-major AGP, Kotlin and Gradle bumps would automerge on a pull-request CI that never runs Gradle; the weekly canary would show the break up to seven days later. Add those managers to the never-automerge carve-out in `renovate.json`, or build the APK on pull requests.
- **The Gradle wrapper script and jar are gitignored** by Flutter's template (`android/.gitignore`); Flutter regenerates them. Renovate's wrapper manager expects to run `./gradlew wrapper` (**assumed** to need handling or disabling).
- **The KGP deprecation** (trial-build item 5) will turn into a hard failure on a future Flutter. It clears when `video_player_android` and `volume_controller` migrate; both are transitive, so the fix arrives through `media_kit_video` and `video_player` bumps.
- **Template drift.** AGP, Gradle and Kotlin versions are frozen at `flutter create` time. Flutter warns, then errors, as they fall behind its supported range (**assumed**); bump them with the Flutter pin.
- **The Ava fork is a git submodule.** A checkout without submodules cannot build `android/`: `settings.gradle.kts` stops with "android/third_party/ava is empty" (**verified**). The APK jobs in both `build-pi-image.yml` workflows check out with `submodules: true`. The Pi and desktop jobs never evaluate `android/` and need nothing.
- **The fork's modules are built by Hearth's scripts**, `android/ava/{esphomeproto,microfeatures,satellite}/build.gradle.kts`, because the fork pins AGP 8.12.3, Kotlin 2.3.10 and Gradle 8.13. They compiled unchanged under AGP 9.1.0, Kotlin 2.4.0 and Gradle 9.3.1 at JVM target 17 (**verified**). Library versions come from the fork's `gradle/libs.versions.toml`, loaded as the `ava` version catalog. The fork's JVM unit tests are not run from Hearth's build; they run in the fork.
- **Renovate does not see the submodule pin** (its `git-submodules` manager is off by default and tracks branches). `scripts/check-upstream-drift.sh` reports the fork against `brownard/Ava`; moving Hearth to a new fork tag is manual.
- **Two more modules apply the Kotlin Gradle Plugin**, `ava-microfeatures` and `ava-satellite`, and join the warning in trial-build item 5 (**verified**). AGP 9.1 has no per-module opt-in (`com.android.built-in-kotlin` is not found, **verified**), so they move when `android.builtInKotlin` is switched on for the whole build.
- **APK size.** The debug APK grew from 228 MB to 249 MB across three ABIs (**verified**). The release arm64 figure is unmeasured.
- **`flutter_inappwebview_android` is pinned to a prerelease, `1.2.0-beta.3`,** with `flutter_inappwebview_platform_interface` at `1.4.0-beta.3`. The last stable release, 1.1.3, calls `getDefaultProguardFile('proguard-android.txt')`, which AGP 9 removed, so the Gradle build fails while evaluating the plugin (**verified**). Move to a stable 1.2 when one ships. Hearth depends on the Android implementation and the platform interface, not the umbrella `flutter_inappwebview`, so the Windows (WebView2, NuGet) and macOS implementations never enter a desktop build; the generated Linux and Windows plugin lists do not name it (**verified**). The plugin adds androidx `webkit`, `browser`, `appcompat` and `swiperefreshlayout`, and Guava's `listenablefuture`, all covered by existing notice entries (**verified** against `:app:dependencies`). A bump of it automerges on a CI that never builds the APK; the weekly canary is the net.
- Pub package bumps keep automerging on analyze + test. That was already true for Pi-only breakage, which the weekly Pi image build catches within seven days. The same weekly run now builds the APK, so Android has the same seven-day net.
